# Quick civilization pick — proposal

Status: implemented locally; awaiting live Discord trial. Branch: `codex/civilization-pick`.

## Experience

Command: `/civpick match_id:123 minutes:3 redo:false`.
Use the bot's ranked match ID, which already has teams and Discord player IDs.
The user confirmed this identifier: the command takes the bot match ID.

- Start only for a current ranked match in this channel with two formed teams.
- Show one shared pool of 12 distinct civs, numbered 1–12, plus `13 · 🎲 Random`.
  Propose keeping 12 options for smaller matches too, for a consistent trial UI.
- Use numbered Discord buttons in three rows, with civ names in the card and
  button labels where practical. No turn order, balancing, bans, or strategy phase.
- Only roster members can claim. First successful atomic claim wins each civ.
  Each player gets one successful choice; a rejected collision does not consume it.
- Random is unlimited: multiple players may select it. It means select Random
  in the game, not ask the bot to assign another civ.
- Update the same card after accepted picks: player names, teams, picked status,
  and players still waiting. Hide player-to-civ assignments until everyone picks
  or time expires. Keep all buttons visually available while open so button
  changes do not reveal choices; reject taken civs privately without spending
  a pick. Invalidated rounds do not reveal choices. Show a Discord relative
  deadline, without a ticking edit loop.
- Finish when everyone picks or time expires (default 3 minutes; proposed range
  1–10 whole minutes). Disable buttons and show the final player-to-civ summary
  on the same card, avoiding duplicate final posts during recovery.
  Confirmed timeout rule: `Random (timed out)` for anyone who did not pick.
- Repeating the command returns the current card or saved final results and does
  not reset the deadline. Only explicit `redo:true` starts a fresh generation,
  clears choices, redraws the pool, and invalidates previous buttons.
- Proposed permissions: participants or channel admins may start; original
  initiator or admins may redo. Rate-limit starts/redo, e.g. once per match per
  30 seconds, with one active generation per match.
- These are voluntary suggestions. Never write a suggested civ into actual-game
  history, ratings, gold, or game settings.

## Variety

Read `civ_pick_history` for this channel with `at >= now - 86400`. Only explicit
civ-button choices enter this history, at acceptance time. Random, automatic
timeouts, and options merely shown in a pool do not count. Actual game results
are not consulted, so civilizations received through in-game Random can return.
Accepted choices remain in the cooldown history even if the round is redone.

Sample unused civs first. If fewer than 12 remain, keep all of them and fill only
the shortage from recently picked civs, preferring lowest frequency, then oldest
last use; randomize ties. Never duplicate a civ inside a pool. With no recorded
history, sample normally; a database failure should be reported rather than
silently treated as empty history. A redo may show any unpicked options again.

Use a checked, supported multiplayer civ catalog. Do not reuse the old balanced
pool's minimum-50-games requirement or win-rate tiers: those would exclude new
civs and introduce balancing the user did not request. The trial includes DLC
civs; players should choose a civ they own or use Random. There is no DLC-account lookup.

## Implementation sequence

1. Add a feature under `features/civs/` with a pure pool selector, card renderer,
   commands, store, interaction router, and deadline handling. Follow existing
   quiz/betting integration patterns through `discord/slash.py`, bootstrap and
   wiring; keep the pickup domain independent of features.
2. Store one small JSON session record, including roster and choices, in existing MySQL.
   Store explicit choices atomically in a separate, indexed history table.
   On creation/redo, remove up to 100 expired history rows for that channel;
   no periodic cleanup is needed. Migration 014 seeds recent legacy choices
   from saved snapshots using round start time (older builds did not store
   individual acceptance times). Already overwritten legacy rounds cannot
   be recovered.
   Scope by channel and bot match ID, with generation, options, deadline,
   initiator, message ID, and terminal status. Retain the latest result for
   repeat commands; superseded generations need not accumulate indefinitely.
3. Serialize claims, timeout, and redo on the same session row lock. Recheck
   generation, roster, status, server time, and availability inside the
   transaction. Ensure one choice per player and one owner per non-Random civ.
4. Acknowledge interactions promptly; serialize/coalesce card edits so an old
   render cannot overwrite a newer result. Bound retries for Discord errors.
   Persist outcomes before rendering; repeated commands can recover a missing
   or stale card without losing selections.
5. Recover open sessions at startup and schedule their deadlines in the existing
   process. Reject expired presses even if final rendering is delayed. No new
   service, per-second database poll, or external game lookup. Use a lightweight
   bounded reconciliation path only for failed terminal rendering.
6. On roster changes, invalidate the active round and require an explicit redo
   with the new roster. On match end/cancellation, close the round. Do not
   introduce game-start polling; this remains a voluntary pre-game tool.
7. Test simultaneous claims, double presses, rejected collisions, multiple Random
   choices, timeout races, redo races, stale buttons, permissions/channel scope,
   restart recovery, roster changes, and variety fallback. Run repository lint
   and required architecture checks, then a manual Discord trial before rollout.

## Cost and risks

Target: negligible added resource use on the existing Railway bot and MySQL,
with no new dependencies, infrastructure, AI calls, replay downloads, or history
scraping. For eight players, normal activity is one initial post, up to eight
accepted-pick updates, and finalization, plus a handful of small DB transactions.
Coalescing can reduce edits. Invalid-click/start spam must be throttled too.

Use a `(channel_id, at)` index on explicit-pick history and avoid scanning all
history on every click. The legacy game-history index from migration 013 remains.
Load history only at creation/redo. Keep only active sessions in memory.

An exact zero bill increase cannot be promised: Railway meters CPU, RAM, storage,
and network. Compare resource usage during a small trial and make the feature
easy to disable. No production usage or billing has been inspected for this plan.

Main functional risks: near-simultaneous presses, latency favoring one player,
incomplete played history, unavailable DLC, substitutions, and restarts midway.
The atomic claim is the definition of first, not the player's local click time.
Handle these explicitly without adding enforcement or strategy features.

## Confirmed decisions

1. Use the bot's ranked match ID.
2. Recent civ exclusions cover explicit civ-button picks in this channel only,
   over the rolling last 24 hours (updated from the original game-history rule).
3. Missing picks become `Random (timed out)` when the deadline expires.

Other proposed defaults above are negotiable: always 12 civs, unlimited Random,
one successful pick, initiator/admin redo, 1–10 minutes, and a common civ catalog.

and rerunning the command recovers the saved choices on the tracked card.
